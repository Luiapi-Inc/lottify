# Lock implementation roadmap and delivery sequencing

Type: grilling
Status: resolved
Blocked by: 01, 02, 03, 04, 05, 06, 07, 08, 09, 10, 11, 12, 13, 14, 15, 16

## Question

What implementation phases, dependency order, work packages, acceptance gates, migration/release checkpoints, and traceability handoff turn the locked Lottify v1 specification into an executable implementation roadmap without reopening approved decisions or implementing product code during this Wayfinder effort?

## Comments

### Implementation roadmap round 1 — confirmed

- Roadmap shape: implementation is organized as dependency-driven vertical milestones rather than completing bounded contexts as isolated silos. Each milestone traverses the applicable Domain/Application rules, persistence/migrations, API/contracts, worker/asynchronous behavior, Member/Admin surface, and tests/evidence needed to prove that capability, while preserving the bounded-context ownership locked in Ticket 01.
- Production-shaped foundation first: the first milestone establishes module boundaries and context ownership, PostgreSQL/Prisma migration discipline, explicit transaction seams, Transactional Outbox and idempotency infrastructure, Redis/BullMQ non-authoritative infrastructure, OpenAPI/generated-client pipeline, authentication/session foundation, observability, immutable container/build/deployment skeleton, and deterministic test harness. This milestone creates the implementation platform but is not itself treated as a usable-product completion claim.
- Financial-core dependency: Ledger, Wallet projection, Reservation, idempotency, uniqueness/concurrency controls, posting/compensation rules, and financial integration-test primitives precede Deposit finalization, Bet Confirm, Refund, Settlement, Withdrawal finalization, and Promotion monetary effects. No downstream vertical may substitute a temporary mutable balance model that would later need to be replaced by the approved financial core.
- Business-vertical order: the default dependency sequence is `Identity/Eligibility → Lottery Configuration/Draw → Wallet + Deposit → Quote/Confirm/Receipt → Result/Settlement/Refund → Withdrawal → Promotion → Reporting/Reconciliation`. This is a dependency order rather than a prohibition on parallel work: independently safe work may overlap, but a milestone cannot claim acceptance while a prerequisite invariant or contract is unresolved. Required Admin capabilities are delivered alongside the vertical they govern rather than deferred into one late Admin phase.
- Milestone Definition of Done: a milestone closes only when its applicable trace is complete across `Locked Requirement/Decision → Implementation → Migration/Data impact → required Unit/Integration/Contract/E2E evidence → Functional/Visual result → Observability → Recovery/Rollback or Roll-forward evidence`. Build success, green CI, code presence, or partial automated-test coverage alone never establishes milestone completion.

### Implementation roadmap round 2 — confirmed

- Provider sequencing: canonical adapter contracts, deterministic fakes/sandboxes, provider/business/attempt identity rules, webhook verification, ambiguity handling, retry/reconciliation seams, and provider contract-test infrastructure are established early enough to support dependent verticals. Production-provider integration is delivered with the vertical that consumes it: KYC with Identity/Eligibility, Payment with Deposit/Withdrawal, Result providers with Result/Settlement, and Notification with the workflows that emit regulated or transactional communication. No vertical is accepted while its provider ambiguity/reconciliation path remains unproved.
- Admin sequencing: Admin is not deferred into a late standalone build. A minimum operational control plane is established early for authorization, re-authentication, audit, approvals, configuration and operational diagnostics, then expanded alongside each governed vertical—for example Lottery/Draw configuration, Payment review, Result/Settlement approval/correction, Reconciliation, Promotion governance and provider/emergency controls. Admin functionality cannot bypass the same domain invariants used by automated or Member flows.
- Security sequencing: security is continuous rather than a final hardening phase. Session rotation/revocation, RBAC plus contextual policy, Admin MFA/re-authentication, immutable audit, secrets handling, webhook authenticity/replay protection, sensitive-data masking and baseline abuse/rate-limit controls are implemented with the first affected vertical. Production-candidate security scanning, race/negative-path verification and penetration/security assessment are later release gates, not substitutes for secure-by-construction implementation.
- Operational-readiness milestone: after the required business verticals are complete, one end-to-end operational-readiness milestone proves cross-context workflows and failure semantics in production-like conditions, including idempotent retries, ambiguous provider recovery, Outbox/queue replay, reconciliation, migration compatibility, observability, backup/restore and critical Member/Admin workflows. This milestone integrates already-approved architecture and invariants; it must not become a holding area for architectural defects that should have blocked earlier milestones.
- Environment/promotion sequence: implementation moves through `local/test → integration/staging → production candidate → production`. Staging is production-like enough for migration compatibility, provider sandbox behavior, observability, performance, security, recovery and release-smoke evidence. A production candidate is an immutable artifact set with reviewed migrations/configuration; production promotion deploys that same candidate artifact rather than rebuilding different binaries for production.

### Implementation roadmap round 3 — confirmed

- Work-package sizing: each implementation work package is a bounded, independently reviewable capability with an explicit owner, source Requirement/Decision identities, affected bounded context/surface, contract and migration/event impact, and the acceptance evidence needed to close it. Broad labels such as "build Wallet" or "build Admin" are decomposition themes rather than executable work packages unless narrowed to a testable capability with clear completion semantics.
- Safe parallelism: work may proceed in parallel only when its prerequisites and write/ownership boundaries are stable and non-conflicting. Examples include Member and Admin presentation work against an already locked/generated contract, or a provider adapter against a settled canonical interface while unrelated domain work proceeds. Shared financial schema/invariants, authoritative API/event contracts, race-sensitive transaction semantics, and migration ordering are serialized until their controlling decisions and compatibility seams are stable.
- Migration/backfill placement: schema/data evolution belongs inside the milestone/work package that creates or changes the affected capability rather than being deferred to a final release bucket. Production change follows `expand → backfill → verify → contract`, includes old/new application compatibility during the rollout window, validates business/data invariants after backfill, and carries the applicable rollback or governed roll-forward plan before that milestone can close.
- Seed/reference configuration: Product, Bet Type, Draw schedule/result/settlement, provider, policy and other required reference/operational configuration are implementation artifacts when the runtime depends on them. They are versioned, reviewed, environment-aware, reproducible, validated and covered by acceptance evidence; undocumented manual production setup is not an acceptable substitute for roadmap work or configuration delivery.
- Implementation handoff record: every roadmap item is handed to implementation with at least `Milestone → Work Package → Source Requirement/Decision IDs → Dependencies → Owning Context/Surface → Contract/API/Event/Migration impact → Test/Evidence obligations → Release gate`. The handoff must be sufficient for an implementation team to execute without silently redefining product behavior, domain invariants, authorization policy, financial semantics or release acceptance.

### Implementation roadmap round 4 — confirmed

- Scope/contract freeze: before a production candidate is declared, the release enters a Scope/Contract Freeze. New feature scope is not admitted after this point unless it is a blocker for an existing GO/NO-GO requirement. API, event, schema, configuration, migration, security-policy or financial-contract changes after freeze require explicit change-impact review across compatibility, acceptance evidence, migration/recovery and affected Member/Admin behavior.
- Release-blocker priority and WIP: blocker priority is `Integrity/Security/Compliance → Functional critical path → Recovery/Operations → Performance → Non-critical UX`. Critical-path blocker work uses a WIP limit of one unresolved blocker at a time unless two tasks are proven independent, so release work does not fragment into parallel changes that obscure root cause, evidence or rollback scope.
- Production rollout: production uses the blue/green discipline locked in Ticket 15: deploy the immutable production candidate to the inactive environment, verify migration compatibility plus health/smoke evidence, switch traffic deliberately, then perform post-deploy verification. Application rollback is allowed only while database compatibility remains valid; otherwise recovery follows the governed roll-forward path rather than ad-hoc data mutation.
- Roadmap completion versus Production GO: resolving this implementation roadmap means the implementation route, dependency order, work-package contract and release checkpoints are decided and handoff-ready. Production deployment remains subject to the Ticket 13/16 engineering release-evidence gates.
- Wayfinder completion gate: after this ticket is resolved, the map is complete only if the Destination/Q154 deliverables—workflow, domain model/glossary, state machines, business rules, permissions/policies, API contract, UX flows, acceptance criteria/test traceability, technology baseline and implementation roadmap—are all represented by resolved source-of-truth tickets, and no in-scope decision ticket or fog remains. Production visual-design-system/component styling and jurisdiction/licensing/legal research are not specification decisions required by this engineering Destination.

## Answer

Lottify v1 implementation proceeds through dependency-driven vertical milestones on a production-shaped foundation. Foundation establishes bounded-context/module ownership, transaction and migration discipline, financial/idempotency/outbox infrastructure, OpenAPI/generated clients, security/observability, immutable deployment artifacts and deterministic test seams. The financial core precedes all money-moving verticals. The default business order is `Identity/Eligibility → Lottery Configuration/Draw → Wallet + Deposit → Quote/Confirm/Receipt → Result/Settlement/Refund → Withdrawal → Promotion → Reporting/Reconciliation`, with the necessary Admin controls and provider integrations delivered alongside each governed capability.

Each implementation work package is bounded, traceable and independently reviewable, with explicit source requirement identities, dependencies, owning context/surface, API/event/migration impact and required acceptance evidence. Safe parallelism is allowed only after shared contracts, financial invariants and migration ordering are stable. Schema/data change stays inside the owning milestone and follows `expand → backfill → verify → contract`; required seed/reference configuration is versioned implementation material, not undocumented production setup.

After the verticals, an operational-readiness milestone proves cross-context failure/recovery, reconciliation, replay, migration compatibility, backup/restore, observability, performance/security and critical Member/Admin flows in production-like staging. A Scope/Contract Freeze precedes the immutable production candidate. Production rollout uses blue/green promotion with compatibility-aware rollback or governed roll-forward recovery. The roadmap is complete when the implementation handoff is executable without redefining approved behavior; Production GO requires the independent engineering release-evidence gates.
