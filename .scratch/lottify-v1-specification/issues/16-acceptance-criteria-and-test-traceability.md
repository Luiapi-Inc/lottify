# Lock acceptance criteria and test traceability model

Type: grilling
Status: resolved
Blocked by: 02, 03, 04, 05, 06, 07, 08, 09, 10, 11, 12, 13, 14, 15

## Question

What acceptance criteria and requirement-to-test traceability prove each approved workflow, financial invariant, state transition, policy decision, API contract, Member/Admin UX flow, recovery path, operational control, and release gate, and which evidence is required before the specification is implementation-ready?

## Comments

### Acceptance/test traceability round 1 — confirmed

- Traceability unit: every testable requirement or locked decision has a stable identity and traces through `Requirement/Decision → Acceptance Criterion → Test Scenario → Test Level → Evidence`. Ticket completion, implementation presence, or a green CI status is not itself acceptance evidence.
- Acceptance-criterion shape: critical acceptance criteria are objectively verifiable and state the precondition, actor/context, triggering action, expected authoritative state/effect, forbidden effect where relevant, and observable evidence. `Given / When / Then` is the preferred representation when it improves clarity, but equivalent precise wording is acceptable.
- Test-level mapping: Unit tests cover pure domain calculations/rules/policies; Integration tests cover PostgreSQL transactions, Ledger invariants, state machines, orchestration and idempotency; Contract tests cover REST/OpenAPI, provider-adapter and event-schema contracts; E2E tests cover critical Member/Admin journeys; NFR/Operational tests cover capacity, recovery, migration, security and observability. A requirement uses only the levels necessary to prove it; every requirement is not forced through every level.
- Financial/state-machine anchor tests: deterministic Integration tests are mandatory anchors for Ledger balance/integrity, reservation concurrency, Bet Confirm, refund, settlement/correction, Withdrawal finalization, idempotency/replay, and illegal state-transition rejection. Unit tests alone are insufficient proof for transactional or cross-state invariants.
- Critical-path scenario coverage: each critical workflow traces the applicable scenarios across happy path, validation rejection, authorization/policy denial, retry/idempotency, concurrency/race, partial or ambiguous failure, and recovery/compensation. Scenarios that do not apply are explicitly marked not applicable rather than silently omitted.

### Acceptance/test traceability round 2 — confirmed

- API contract evidence: every `/api/v1` operation traces to contract tests covering request/response schema, authentication/authorization expectations, common and domain error codes, idempotency/concurrency semantics where applicable, and compatibility checks against the authoritative OpenAPI contract. Generated-client success alone is not sufficient evidence of behavioral compatibility.
- Member/Admin UX acceptance: critical Member and Admin journeys have end-to-end acceptance scenarios that prove both the authoritative functional result and the user-visible state. Required journeys include at least Quote → Confirm → Receipt, Withdrawal, correction/history visibility, and governed Admin approval/configuration publish/reconciliation flows. Screenshots or visual snapshots may supplement evidence but cannot replace functional verification.
- Provider/async evidence: provider and asynchronous reliability contracts are proven with contract/integration scenarios for webhook authenticity/signature and replay protection, duplicate delivery, timeout/ambiguous outcome handling, retry/DLQ/replay, and Transactional Outbox crash/redelivery. Evidence must show that replay/redelivery can occur while the authoritative business or financial effect remains once-only.
- Evidence artifacts: each acceptance execution records at least the Requirement/Decision or Acceptance Criterion identity, test/scenario identity, environment and immutable build/release identity, result, execution timestamp, and a machine-readable or durable evidence/log/report reference sufficient for later audit. Performance, security, migration/recovery, and other specialist gates retain their corresponding detailed reports in addition to the trace record.
- Traceability completeness gate: a release-critical requirement cannot be marked complete while any required Acceptance Criterion, applicable test scenario/level, or mandatory evidence artifact is missing. Existing implementation, partial test coverage, or green CI cannot waive a traceability gap; missing mandatory evidence remains an explicit NO-GO condition.

### Acceptance/test traceability round 3 — confirmed

- Security acceptance evidence: the traceability model requires positive and negative-path evidence for authentication/session/OTP/MFA/re-authentication, RBAC and contextual-policy denial, maker-checker/separation-of-duties approval controls, webhook replay/authenticity protection, secrets/PII non-leakage, and abuse/rate-limit behavior. Security-sensitive authorization and denial paths are mandatory evidence rather than optional supplemental tests.
- Migration acceptance: every production schema/data change traces to compatibility tests covering old and new application versions across the rollout window, migration execution, backfill/data-integrity verification, and the applicable rollback or governed roll-forward path. A migration that executes successfully but leaves incorrect or incompatible business data fails acceptance.
- Backup/PITR recovery evidence: restore acceptance proves more than database availability. Evidence verifies the Ticket 13 `RPO <= 5 minutes` and `RTO <= 60 minutes` objectives together with Ledger balance/invariants, schema/migration state, critical business references, and resumability or safe reconciliation of in-flight critical workflows after restore.
- Performance acceptance evidence: Ticket 13 capacity and latency targets are exercised in production-like conditions, including realistic pre-cutoff burst behavior, 5,000 concurrently active Member sessions, Quote/Confirm/payment-webhook throughput, queue lag, and settlement of at least 100,000 Bet Lines within 10 minutes. Load evidence also verifies that retries/concurrency do not duplicate financial or other critical business effects.
- Production GO/NO-GO trace: each release candidate maintains an evidence matrix spanning `Requirement → Approved Specification → Implementation → Tests → Functional/Visual Result → Performance/Security → Migration/Backup/Restore → Deployment → Rollback/Roll-forward Recovery`. Any mandatory missing or failed evidence cell is a NO-GO regardless of build, lint, unit-test, or CI status.

### Acceptance/test traceability round 4 — confirmed

- Acceptance-evidence ownership: the owner of the approved requirement/specification defines or approves its Acceptance Criteria. Implementation and test work may produce evidence, but they do not redefine the criterion to fit the implementation. Release review evaluates evidence against the same approved source of truth and records any mismatch as a traceability gap or change request.
- UI/UX acceptance baseline: Member/Admin acceptance is evaluated against the approved UX flow and design specification, including interaction behavior, user-visible normal/error/recovery states, and accessibility requirements where specified. Existing UI is not an acceptance baseline when the approved specification requires a redesign, and screenshots alone do not prove functional acceptance.
- Determinism and flakiness: release-critical tests must be deterministic or execute under controlled reproducible inputs such as seeded data, controllable time, deterministic provider simulations, and isolated state. An unexplained flaky result remains unresolved evidence; rerunning until green does not convert it into acceptance.
- Change impact on evidence: a change to a requirement, approved specification, API contract, lifecycle/state invariant, policy, or other traced decision triggers traceability impact analysis. Affected Acceptance Criteria, scenarios, tests, and prior evidence are invalidated or explicitly re-evaluated; historical passing evidence is not automatically valid for the changed contract.
- Specification-ready gate: Tickets 01–15 must each have a risk-appropriate proof path from approved decision to Acceptance Criteria, scenarios/test level, and required evidence, with no release-critical requirement lacking a verification route. Jurisdiction-specific legal/compliance obligations remain dependencies of Tickets 17/18 and are not invented inside this ticket before those decisions/research are complete.

## Answer

Lottify v1 uses a stable requirement-to-evidence traceability model rather than treating implementation presence or green CI as acceptance. Every testable approved decision traces through `Requirement/Decision → Acceptance Criterion → Test Scenario → Test Level → Evidence`, with objective criteria, explicit negative/recovery coverage where applicable, and durable evidence tied to an immutable build/environment identity.

Test levels are selected by the invariant being proved: pure rules use Unit tests; transactional/state/financial behavior is anchored by deterministic Integration tests; REST/OpenAPI, provider and event compatibility use Contract tests; critical Member/Admin journeys use E2E tests; and capacity, migration, recovery, security, observability and operational behavior use NFR/Operational evidence. Financial correctness, state-machine legality, idempotency/replay, concurrency, settlement/correction and Withdrawal finalization cannot be accepted from Unit coverage alone.

Critical workflows cover the applicable happy, rejection/denial, retry/idempotency, race, ambiguous/partial failure, and recovery/compensation scenarios. API, provider/async, UX, security, migration, PITR/restore and Ticket 13 performance targets each have explicit evidence requirements. Release evidence is reviewed against the approved source of truth; implementation teams do not weaken criteria to match code, screenshots do not replace functional UX evidence, and unexplained flaky tests remain unresolved.

Any traced requirement/specification change triggers impact analysis and re-evaluation of affected criteria/tests/evidence. Production GO requires the complete evidence chain `Requirement → Approved Specification → Implementation → Tests → Functional/Visual Result → Performance/Security → Migration/Backup/Restore → Deployment → Rollback/Roll-forward Recovery`; any mandatory missing or failed evidence is NO-GO. Jurisdiction-specific compliance acceptance remains intentionally deferred to Tickets 17/18 rather than being guessed here.
