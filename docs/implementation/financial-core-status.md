# Financial core milestone implementation status

Source of truth: Wayfinder Tickets 04, 16, and 19. This record does not redefine those requirements.

## Accepted checkpoints

- Member Ledger buckets are locked to `CASH`, `BONUS`, and `LOCKED`.
- THB v1 posting amounts are represented as exact integer minor units (satang) rather than binary floating point.
- A financial posting set must contain at least two positive postings and balance total debit to total credit before it can be accepted by the domain invariant layer.
- Wallet availability follows the locked formula `posted spendable balance - active reservations`.
- Active Reservation amounts must be positive, and a new Reservation is rejected when it would exceed the remaining available spendable balance.
- Immutable Financial Transaction/posting and durable Reservation persistence are implemented with business/correlation/idempotency identity, domain references, timestamps, Reservation allocations, release/consume state, and correction linkage fields required by the current financial-core contracts.
- Reservation create/release is idempotent and persistence-backed. Reservation creation serializes the authoritative account state so concurrent requests cannot overspend the same available balance.
- Reservation consumption and its resulting Ledger posting are atomic in one PostgreSQL transaction. The final Member debit postings use the persisted Reservation source allocation, preserving accepted mixed `CASH`/`BONUS` funding rather than recomputing from current balances.
- Released Reservations cannot be consumed. Exact idempotent consume replay returns the original Financial Transaction; conflicting replay is rejected; concurrent alternate consume identities produce one financial effect only.
- Member Wallet projection is derived from authoritative Ledger postings plus active Reservation allocations in one repeatable-read snapshot across `CASH`, `BONUS`, and `LOCKED`; missing buckets project as zero rather than becoming an alternate balance authority.
- `LOCKED` value is never exposed as available spendable balance. Withdrawal Reservation sources remain `CASH` only, and Bet Reservation sources are restricted to `CASH`/`BONUS` so `LOCKED` cannot be consumed as stake.
- Financial REVERSAL is a dedicated operation that derives exact inverse postings from the immutable original transaction; callers cannot submit arbitrary reversal postings through the generic posting path.
- Exact reversal is once-only per corrected transaction and concurrency-safe. Business-semantic COMPENSATION remains an explicit balanced posting linked to a real corrected transaction, with normal financial idempotency/replay semantics.
- A negative posted Member `CASH` position is treated as an active debt/recovery restriction for Wallet availability. While it remains negative, all Wallet buckets expose zero available spendable value and new `BET`/`WITHDRAWAL` Reservations are rejected; bonus-only betting cannot bypass the recovery restriction.
- Known operation semantics are now enforced at the financial boundary: `DEPOSIT_CREDIT` may post Member value only to `CASH` and must include a Member `CASH` credit; `BET_STAKE_COMMIT` can consume only a `BET` Reservation; and `WITHDRAWAL_FINALIZE` can consume only a `WITHDRAWAL` Reservation. These guards prevent one workflow's durable financial hold/effect from being relabeled as another operation.
- Approved v1 Fee Policy Change Request: Deposit and Withdrawal fee quotes default to `0` minor units when Payments configuration does not resolve a non-zero fee. A zero fee creates no separate fee Ledger posting obligation; future non-zero fee effects remain subject to Ticket 04 explicit-posting rules.
- Approved Accounting Period modes Change Request: v1 supports **Automatic weekly** periods and **Custom** periods whose explicit start/end boundaries are defined by an authorized Admin. This supersedes the prior monthly-only cadence decision. Accounting timezone, exact weekly boundary, Custom authorization/validation, ownership/creation, overlap/gap, bootstrap/backfill, close metadata/workflow, and reconciliation-exception controls remain unresolved.

## Current source blocker

Accounting-period/effective-time enforcement remains blocked by missing implementation semantics in the approved source of truth. Tickets 04/14 now lock the required outcomes plus two v1 modes—Automatic weekly and Custom—while every Financial Transaction must belong to one authoritative accounting period, CLOSED history cannot be mutated/backdated, later corrections post in a current OPEN period, and close depends on reconciliation/approved exceptions. The unresolved points are accounting timezone, exact automatic-week boundary, period creation/ownership, Custom authorization/validation, overlap/gap rules, bootstrap/backfill treatment for existing Financial Transactions, period identity/close metadata, and the concrete close-gate workflow for reconciliation exceptions. No Accounting Period schema/API/Admin behavior has been invented beyond the approved mode-level decision.

Fee posting is now partially unblocked by the approved `docs/changes/2026-09-05-v1-zero-default-payment-fee.md` Change Request: the v1 default is zero when no configured fee resolves, and zero creates no fee Ledger posting obligation. Ticket 04 still requires any future non-zero fee to be an explicit traceable Ledger posting, while Q114 still requires provider/method/amount configurability and pre-confirmation visibility. Non-zero fee payer, gross/net treatment, Withdrawal Reservation inclusion, and fee-account ownership/allocation remain unresolved and are not being invented in the financial core.

## Remaining financial-core requirements

This checkpoint does not complete the financial-core prerequisite in Ticket 19. The following approved requirements still need implementation and acceptance evidence before money-moving downstream verticals can claim completion:

1. Accounting-period/effective-time enforcement, including rejection of postings/backdating into CLOSED periods and current-period correction linkage. Implementation is source-blocked as recorded above.
2. Recovery/debt behavior beyond the accepted negative-`CASH` guard where debt is represented by a recovery receivable or another policy-governed unresolved state; the approved sources do not yet define that persistence/policy lifecycle.
3. Zero-default Deposit/Withdrawal fee behavior is approved and implemented as a Payments domain seam. Provider/method/amount configuration persistence and non-zero fee charge/allocation semantics remain source-blocked until the Payments vertical defines them. Known Deposit/Bet/Withdrawal operation guards are accepted, while remaining Win/Refund/Bonus operation-specific posting paths still require their owning vertical seams and deterministic evidence.
4. Durable reconciliation/discrepancy behavior across Ledger ↔ Wallet projection and the later dependent provider/betting/promotion seams; monetary resolution must use approved Adjustment/Compensation rather than direct balance edits.
5. Remaining deterministic Integration evidence required by Ticket 16 for each financial capability and downstream financial finalization as those work packages become eligible.

## Milestone disposition

The persistence/concurrency, atomic-consume, authoritative Wallet-projection, financial-correction, negative-`CASH` debt/recovery guard, known operation-posting semantics, and zero-default Fee Policy contract are accepted, but the financial core is not yet complete. Accounting Period and non-zero fee charge/allocation semantics remain source-blocked, and Withdrawal finalization plus other downstream money-moving acceptance remain blocked until the remaining Ticket 04/16/19 prerequisites above are implemented and proven.
